================================================================================
1. LE PROJET EN UNE PAGE
================================================================================

LibreVies est un jeu (MMO open world low-poly) developpe par l'utilisateur
("Dragonus" sur GitHub : killdrago). Le jeu est une application UNITY :
une seule scene (compilation/unity/Assets/Scenes/LibreVies.unity) et tout le
jeu construit par code C# dans compilation/unity/Assets/Scripts/LibreViesGame.cs
(~35 Ko) : village, chateau, personnage, ennemis, combat, HUD, sauvegarde.
Version du jeu : 0.5.0 en preparation (Unity, export Windows 64 bits Mono).
Derniere MAJ livree : 0.4.0. La 0.5.0 corrige le monde magenta, la camera sous
le sol et la souris molle (MAJ 7) : elle doit encore etre compilee et publiee.

Le but de la refonte terminee ici est la DISTRIBUTION :
  - l'utilisateur ne veut plus envoyer le projet entier aux joueurs ;
  - le joueur recoit UN SEUL fichier : LibreVies.exe (le launcher compile) ;
  - le launcher telecharge tout seul le jeu complet et ses mises a jour ;
  - Unity, Python, PyInstaller, GitHub, le projet Unity et les images de
    travail restent strictement chez l'auteur.

Parcours du joueur :
  double-clic sur LibreVies.exe
    -> verifie les mises a jour sur GitHub
    -> telecharge le jeu complet (1re fois) avec reprise si la connexion coupe
    -> installe dans game\ (controle md5)
    -> bouton JOUER -> le jeu Unity demarre

2. CONTRAT DE STRUCTURE - A NE JAMAIS CASSER
================================================================================

Le depot contient exactement deux dossiers fonctionnels :

  jeu/                 TOUT CE QUI CONCERNE LE JOUEUR, DANS UN SEUL DOSSIER
    launcher.pyw       le launcher (source ; compile en LibreVies.exe)
    version_url.json   le manifeste lu par le launcher
    LIS-MOI.txt        explication envoyee au joueur
    [LibreVies.exe]    le launcher COMPILE, depose ici par le build (ignore par git)
    [game/]            le jeu : export Unity depose par le build, ou telecharge
                       par le launcher chez le joueur (ignore par git)
    [etat_jeu.json]    etat de l'installation (ignore par git)
    [jeu.download.part] telechargement en cours (ignore par git)

  compilation/         SERT UNIQUEMENT A COMPILER - JAMAIS telecharge par le joueur
    unity/             le projet Unity (le jeu)
    build_launcher.bat compile et depose tout DANS jeu\ (LibreVies.exe + game\)
    build_unity_game.bat  export Unity seul (diagnostic)
    setup_unity_build_tools.bat + download_unity_hub.ps1  installent Unity
    image/             images de travail (bannieres, chapitres, logos)
    outils/            publier_jeu, definir_url_publication, creer_icone,
                       test_launcher (la recette)
    [build/]           fichiers de travail du build (ignore par git)

+ README.md (2 sections : joueur / auteur) et resumer.txt (ce fichier).

REGLES :
  - le build DEPOSE ses resultats dans "jeu/" : c'est la demande explicite de
    l'utilisateur ("au joueur il aura tous dans un seul dossier") ;
  - rien de "compilation/" (sources Unity, images, outils) n'arrive dans "jeu/"
    et le launcher n'en telecharge jamais ;
  - "jeu/" ne contient que : launcher.pyw, version_url.json, LIS-MOI.txt,
    plus LibreVies.exe et game/ produits par le build ou par le launcher.


================================================================================
3. COMMENT FONCTIONNE LE LAUNCHER (jeu/launcher.pyw, version 4.0.0)
================================================================================

Le launcher est un fichier Python unique de ~650 Ko : ~1080 lignes + les
images (banniere, icone, ICO) integrees en base64. Il n'a besoin d'AUCUNE
bibliotheque externe : tkinter (livre avec Python) et, si present, Pillow
(facultatif : sans lui, les PNG integres passent par tk.PhotoImage).

3.1 Au lancement (1er passage)
  - GAME_DIR = dossier du .exe (ou du .pyw en developpement).
  - Il lit jeu/version_url.json recopie a cote de lui. S'il n'existe pas, il
    utilise DEFAULT_RAW_URL ecrit en dur (valeur de secours).
  - Il lit le manifeste distant (raw_url) : URL GitHub "raw".

3.2 Mise a jour des petits fichiers (cle "files" du manifeste)
  - Uniquement des fichiers TEXTE (md5 calcule sur le contenu normalise LF/CRLF).
  - Quand on developpe avec launcher.pyw, les entrees launcher.pyw et
    LibreVies.exe sont ignorees (sinon on ecraserait ses propres sources).
  - Les chemins sont valides par _safe_local_path() : refus des chemins
    absolus, des lecteurs Windows (C:) et de tout "..". Un manifeste corrompu
    ne peut donc pas ecrire hors du dossier du launcher.
  - Le launcher compile (LibreVies.exe) ne peut pas se remplacer pendant qu'il
    tourne : il depose .new puis un .cmd remplace le fichier apres fermeture et
    relance le launcher.

3.3 Mise a jour du JEU COMPLET (cle "game_build" du manifeste)
  C'est le coeur de la distribution. Le jeu n'est PAS telecharge fichier par
  fichier : il arrive en UNE SEULE archive .zip.

    {
      "game_build": {
        "moteur": "unity",
        "version": "0.4.0",
        "dossier": "game",           <- ou l'archive est installee
        "exe": "LibreViesGame.exe",  <- lance par le bouton JOUER
        "url": "https://github.com/.../releases/download/derniere/LibreVies_jeu_xxxx.zip",
        "size": 39269570,
        "hash": "md5 de l'archive"
      }
    }

  Deroulement de installer_build_jeu() :
    1. telechargement dans jeu.download.part avec en-tete HTTP Range si un
       fichier partiel existe (reprise), verif que le serveur repond bien 206
       sinon on repart de zero, barre de progression en Mo ;
    2. controle de la TAILLE puis du MD5 annonces par le manifeste. Si l'un des
       deux est faux : l'archive est effacee et l'installation existante reste
       intacte (le joueur peut toujours jouer) ;
    3. extraction dans game.install\ avec protection contre les archives
       piegees (tout chemin contenant "..", absolu ou avec "C:" est refuse) ;
    4. si l'archive contient un unique dossier racine, il est "remonte" ;
    5. recherche de l'executable (LibreViesGame.exe) ;
    6. remplacement ATOMIQUE : l'ancienne installation devient game.ancien\,
       la nouvelle game\, puis game.ancien\ est supprime. En cas d'echec, on
       remet l'ancienne en place ;
    7. etat enregistre dans etat_jeu.json (hash, version, exe, date) ;
    8. archive supprimee.

  build_a_installer() decide s'il faut (re)telecharger :
    - pas de hash dans le manifeste -> "aucune compilation Unity publiee"
      (message affiche au joueur, bouton JOUER grise) ;
    - hash different de etat_jeu.json -> "nouvelle compilation disponible" ;
    - hash identique mais jeu absent/casse -> "fichiers du jeu a reparer" ;
    - sinon -> "jeu a jour".

3.4 Etat vide du manifeste (IMPORTANT pour comprendre l'etat actuel)
  Aujourd'hui jeu/version_url.json a "game_build": {} et "files": {}.
  Cela veut dire : AUCUNE compilation n'a encore ete publiee. Le launcher
  affiche donc "aucune compilation Unity publiee" et le bouton JOUER reste
  grise. C'est voulu : c'est la premiere publication (section 4) qui remplit
  ce bloc, et tout devient automatique ensuite.


================================================================================
4. PUBLIER UNE MISE A JOUR (procedure normale, cote auteur, sous Windows)
================================================================================

  1. compilation\build_launcher.bat   (double-clic)
     Il telecharge ce qui manque (voir section 6) puis COMPILE et DEPOSE tout
     dans le dossier jeu\ :
        jeu\LibreVies.exe   <- LE fichier a donner au joueur
        jeu\game\           <- le jeu a publier
     A la fin il demande : "Publier cette compilation maintenant ? [O/N]"

  2. Repondre O  -> il enchaine sur outils\publier_jeu.bat, qui :
       - rassemble jeu\game en UNE archive LibreVies_jeu_<md5>.zip ;
       - l'envoie dans la release GitHub "derniere" (gh release upload) ;
       - ecrit url/size/hash/moteur/exe/version dans jeu/version_url.json ;
       - publie aussi jeu\LibreVies.exe (cle "files"/"LibreVies.exe")
         pour que les launchers deja installes se mettent a jour ;
       - note l'installation locale dans jeu\etat_jeu.json : le launcher d'ici
         affiche "jeu a jour" sans retelecharger ce qui vient d'etre compile ;
       - avec --pousser : git add/commit/push du manifeste.

  3. Les joueurs recoivent la mise a jour au prochain lancement.

  Le nom de l'archive contient son md5 : une nouvelle publication ne remplace
  jamais l'archive sous les pieds d'un joueur en train de telecharger.
  Sans gh installe, publier_jeu.py cree quand meme l'archive et le manifeste
  et affiche l'URL exacte ou deposer le .zip a la main.

  MAJ 7 - Monde magenta, camera sous le sol, souris molle : corriges
    C'est la MAJ qui repond aux 3 bugs signales par l'utilisateur avec la
    capture d'ecran du monde entier en rose fluo (upload image-1.png), puis
    "fait moi pareil mais en unity" (reprendre le jeu de la branche de
    reference arena/01a09a4d-librevies).

    a) MONDE MAGENTA. Cause : le jeu cree TOUS ses materiaux par code avec
       Shader.Find("Standard"). Unity supprime de la build les shaders
       integres qu'aucun materiau du projet ne reference ; dans l'exe compile
       Shader.Find renvoyait donc null, et Unity affiche en magenta tout objet
       dont le materiau n'a pas de shader valide. Correctif : nouveau shader
       du projet Assets/Resources/LVShaders/LVColor.shader (tout ce qui est
       dans un dossier Resources est TOUJOURS embarque dans la build) et
       chaine de secours dans ResoudreShader() :
         Standard -> Resources LVColor -> Unlit/Color -> Sprites/Default ->
         UI/Default -> (echec total : Debug.LogError + materiau null)
       Le shader retenu est ecrit dans la console (Debug.Log) pour diagnostiquer
       en une ligne chez le joueur. Les .meta des deux shaders sont ecrits a la
       main avec des GUID fixes (a1b2c3d4e5f60718293a4b5c6d7e8f90 et
       0f1e2d3c4b5a69788796a5b4c3d2e1f0) : Unity les importe tels quels.

    b) CAMERA QUI DEMARRE SOUS LE SOL. Cause : la camera orbitait avec
       Quaternion.Euler(cameraPitch = +18) * Vector3.forward, ce qui envoie la
       camera VERS LE BAS (a l'ouverture : y = -0,85, donc sous le village,
       d'ou l'ecran qui part du sol et remonte). Correctif : Vector3.back
       (la camera se place derriere ET AU-DESSUS du heros) + filet de securite
       identique a celui de la reference : jamais a moins de 0,6 au-dessus de
       TerrainHeight(x, z). La vue 1re personne regarde desormais dans l'axe
       du pitch (Quaternion.Euler(-pitch, yaw, 0)) au lieu de la rotation du
       personnage.

    c) SOURIS "LONGUE A LA DETENTE". Deux causes cumulees : Input.GetAxis
       lisse les mouvements, et la sensibilite valait 0,3 alors que la
       reference utilise 0,3 degre par pixel, soit 3 avec le facteur 0,1 que
       Unity applique a Mouse X/Y (10 fois trop lent). Correctif :
       Input.GetAxisRaw + sensibilite 3, reglable avec [ et ], memorisee dans
       PlayerPrefs ("cameraSensitivity") et affichee dans le panneau Options.
       Le clic droit pour tourner la camera est conserve (comme la reference).

    d) RENDU ALIGNE sur la reference : ciel bleu vif avec horizon chaud
       (Skybox/Procedural regle sur _SkyTint 0.30/0.46/0.78, _GroundColor
       0.45/0.50/0.26, _Exposure 1.35 ; repli sur le shader du projet
       Assets/Resources/LVShaders/LVSky.shader), soleil energie 1,3, couleur
       (1 ; 0,90 ; 0,74), rotation (52, -32, 0), lumiere ambiante tricolore et
       brouillard adouci (densite 0,0022), champ de vision 55 (celui de la
       Camera3D de la reference, au lieu de 65).

    - VERIFIE : accolades 122/122, parentheses 687/687, crochets 30/30 dans

  MAJ 8 - Parite gameplay avec la reference : on ne traverse plus les murs

      passes, elagage par portee. Fonctions : ColCercle, ColBoite,
      ResoudreCollisions, HauteurSupport, DansVillage, DistRoute, ClotureEntre.
    - Ce qui est enregistre comme obstacle : les 9 maisons (0,5 m de marge),
      le donjon + les 4 tours + la porte du chateau, le bassin de la fontaine,
      les 2 gardes, les 75 troncs d'arbres, les 22 caisses, et le corps de
      chaque monstre (il suit la bete et disparait a sa mort).
    - Le saut fait 1,60 m (8 m/s, gravite 20) : on saute donc sur les caisses
      et par-dessus la cloture de 1 m, et on atterrit dessus (HauteurSupport).
      La route est pavee : les pieds ne s'enfoncent plus dedans (+0,10 m).
    - La cloture du village est un ANNEAU (rayon 26) bloqueur, sauf la ou passe
      la route. Elle est dessinee avec 96 poteaux comme la reference, et les
      deux portails ont des poteaux doubles de 5,20 m, un linteau, un panneau
      en deux planches et le texte "LIBREVIES" (TextMesh, ignore proprement si
      aucune police n'est disponible).
    - Les monstres : errance quand le heros est loin (0,6x vitesse, direction
      changee toutes les 1,5 a 4 s, 35 % de pauses), poursuite a moins de
      10 m (1,4x), arret a 1,5 m, resolution des collisions (ils ne traversent
      plus rien), et interdiction DEFINITIVE d'entrer dans le village (ils
      longent la cloture) ; un monstre egare est remis dehors d'office.
    - Combat aligne : cadence 0,50 s, portee 2,40 m, tous les ennemis a portee
      sont touches, et INTERDIT de frapper a travers la cloture (ClotureEntre).
    - Ramassage aligne : caillou 3,0 m puis retour apres 20 s, piece 3,5 m puis
      retour apres 60 s, et tout ce qui est a portee est ramasse d'un coup.
    - VERIFIE : accolades 159/159, parentheses 871/871, crochets 40/40. Pas de
      compilateur C# ici : la compilation reelle se fait chez l'utilisateur, et
      la correction ne vaut que si l'exe compile.
    - RESTE DE LA PARITE A FAIRE (voir le TODO) : gardes qui patrouillent les

  MAJ 10 - Decor du village comme la reference (lot demande par l'utilisateur)
    Probleme : le village etait nu (seulement 22 caisses posees au hasard, dont
    certaines dans les murs ou sur la route) et les sapins etaient des
    cylindres empiles.

    - Maillage procedural (classe Maillage) : c'est le seul moyen d'avoir des
      CONES a notre sauce (Unity n'a que cube/sphere/cylindre/capsule) et des
      touffes d'herbe faconnees. Une seule soupe de triangles, normales
      recalculees, aucun asset externe.
    - Sapins : tronc epais + souche + 4 renforts + 3 cones de feuillage (verts
      de plus en plus clairs vers le haut), exactement le modele de la
      reference. 80 sapins disperses, avec des regles qui manquaient :
      JAMAIS sur la route ni dans un batiment (c'etait le cas avant : des
      arbres poussaient sur la route).
    - 6 arbres ronds (tronc + 2 masses de feuillage) aux positions de la
      reference.
    - Herbe : 3 nuances x 140 touffes = 420 touffes dans 3 maillages seulement
      (l'equivalent du MultiMesh de la reference) : aucun cout visible.
      Regles reprises : rien sur la route, rien au milieu du village.
    - Rochers : 2 nuances x 45, hexaedres deformes, poses comme dans la
      reference (jamais sur la route, jamais sur la clouture du village),
      bloquants sauf ceux poses sur la route.
    - Barils (5) pres de l'auberge et de la forge, caisses (positions de la
      reference + 2 libres), petites cloutures le long de la route,

6. JOURNAL DES PROBLEMES RENCONTRES ET DE LEURS SOLUTIONS
   (a lire avant de "corriger" quoi que ce soit : la plupart sont des pieges)
================================================================================

INCIDENT 1 - Le depot melangeait deux moteurs (l'ancien + Unity)
  Symptome : plusieurs branches avec des versions differentes du jeu ; le
  manifeste pointait un coup vers l'ancien moteur, un coup vers Unity.
  Cause    : historique du projet (portage de l'ancien moteur vers Unity par
  une autre IA) ; la branche de travail choisie par l'utilisateur est celle
  d'Unity.
  Solution : decision de l'utilisateur = UNITY UNIQUEMENT. Toutes les traces
  de l'ancien moteur ont ete retirees du depot (manifeste, launcher, outils,
  commentaires).
  Reste a faire : 3 archives de l'ancien moteur (~117 Mo) trainent dans la release
  GitHub "derniere" (LibreVies_Windows*.zip). Plus rien ne pointe dessus.
  Attente de la decision de l'utilisateur pour les supprimer.

INCIDENT 2 - Le modele "un fichier par fichier" ne tenait pas
  Symptome : package.files devait lister chaque fichier de la build (dll,
  dossiers *_Data, ressources...) avec son md5. Des centaines d'entrees a
  regenerer a chaque build, et une coupure de connexion obligeait a tout
  reprendre.
  Solution : le jeu est publie en UNE archive .zip identifiee par son md5.
  make_package_manifest.py (qui generait ce manifeste par fichier) a ete
  supprime ; c'est publier_jeu.py qui remplit game_build.

INCIDENT 3 - L'etape "icone" du build echouait TOUJOURS
  Symptome : le build s'arretait avec "ERREUR : impossible de creer icon.ico".
  Cause : le script utilisait python -c "... spec_from_file_location('lv',
  'launcher.pyw') ...". spec_from_file_location ne reconnait pas l'extension
  .pyw : il renvoie None et module_from_spec plante (AttributeError).
  Solution : nouvel outil compilation/outils/creer_icone.py qui utilise
  importlib.machinery.SourceFileLoader (qui charge n'importe quelle extension),
  verifie l'en-tete du .ico et la taille. Si l'icone echoue, le build CONTINUE
  sans icone au lieu de s'arreter.

INCIDENT 4 - Le telechargement du projet ecrasait des fichiers locaux (risque)
  Symptome : aucun, mais le risque etait reel : si on ecrase le dossier de
  l'auteur avec l'archive GitHub, on perd son travail en cours.
  Solution : robocopy /E /XC /XN /XO (copie uniquement ce qui est ABSENT).
  Verifie par simulation : les fichiers deja presents sont intacts.

INCIDENT 5 - PyInstaller ne trouvait pas l'icone (rapporte par l'utilisateur)
  Symptome exact :
    FileNotFoundError: Icon input file
    ...\compilation\build\icon.ico not found
    (le .ico existait pourtant dans ...\compilation\icon.ico)
  Cause : PyInstaller resout un chemin d'icone RELATIF au dossier du fichier
  .spec (--specpath, donc build\), pas au dossier courant.
  Solution : passage du chemin ABSOLU et entre guillemets:
      set "ICONE_ARG=--icon="%ROOT%icon.ico""
  Le double guillemet externe de set "VAR=..." et les guillemets internes
  sont volontaires : le dossier de l'utilisateur contient des espaces
  (C:\Users\Dragonus\Desktop\Jeu\LibreVies\unity2\compilation\...).

INCIDENT 6 - LibreVies.exe aspirait pygame/numpy
  Symptome (visible dans le journal du build) : PyInstaller analysait
  hook-pygame/hook-numpy/hook-PIL/hook-psutil et "pygame 2.6.1 ... Hello from
  the pygame community" s'affichait pendant le build.
  Cause : ces paquets sont installes dans le Python de l'auteur ; un fichier
  .pth de site-packages provoque leur import pendant l'analyse, et PyInstaller
  embarque tout ce qu'il a vu -> executable inutilement enorme.
  Solution : --exclude-module pygame --exclude-module numpy --exclude-module
  psutil --exclude-module setuptools --exclude-module pip (aucun n'est utilise
  par le launcher). Pillow reste inclus : il sert a redimensionner la banniere.

INCIDENT 7 - Un de mes outils a corrompu le launcher (le plus grave)
  Symptome : IndentationError: unexpected indent, launcher.pyw line 88.
  Cause : definir_url_publication.py (1re version) remplacait DEFAULT_RAW_URL
  avec une REGEX multi-lignes trop gourmande : elle a avale le bloc
  "def start_update" qui suivait.
  Solution : remplacement LIGNE PAR LIGNE (on part de la ligne qui commence
  par "DEFAULT_RAW_URL" et on compte les parentheses), plus deux garde-fous :
  compile() sur le resultat et comparaison du nombre de lignes. Rien n'est
  ecrit si l'un des deux echoue. Le launcher a ete reconstruit depuis git.
  LECON : ne jamais modifier launcher.pyw avec une regex multi-lignes ; et
  toujours verifier avec py_compile/compile() avant/arriere.

INCIDENT 8 - cmd.exe : parentheses dans un echo a l'interieur d'un bloc
  Symptome : erreur de syntaxe du .bat, ou texte tronque.
  Cause : dans un bloc ( ... ), une parenthese non echappee ferme le bloc.
  Solution : ^( et ^) partout dans les echo places dans un bloc.
  Comme le developpement se fait sous Linux (pas de cmd.exe), un CONTROLEUR
  Python verifie chaque .bat : equilibre des blocs, parentheses en milieu de
  ligne, guillemets impairs, et presence des etiquettes (labels) appelees.
  Ce controle a trouve une vraie faute : une ligne "echo ... l''acces ..."
  (double apostrophe) corrigee.

INCIDENT 9 - choix [O/N] avec une logique inversee
  Cause : errorlevel de choice = INDEX de la touche (1 pour O, 2 pour N), pas
  un code d'erreur ; "if errorlevel 1" est donc vrai dans les deux cas.
  Solution : "if errorlevel 2 goto :fin" puis "if not errorlevel 1 goto :fin"
  (seul un O explicite lance la publication).

INCIDENT 10 - Tester le launcher sans tkinter (bac a sable Linux)
  Cause : tkinter n'est pas installable/installé dans l'environnement de
  developpement de l'IA.
  Solution : la recette (outils/test_launcher.py) injecte un faux module
  tkinter dans sys.modules et charge le launcher avec SourceFileLoader. On
  teste ainsi TOUTE la logique (telechargement, md5, installation, reprise,
  securite) sans interface graphique.

INCIDENT 11 - Chez le joueur : ecriture impossible a cote du launcher
  Cause : si LibreVies.exe est dans C:\Program Files, Windows interdit
  l'ecriture et le jeu ne peut pas s'installer.
  Solution : LIS-MOI.txt demande de mettre LibreVies.exe sur le Bureau, dans
  Documents ou sur une cle USB.

INCIDENT 12 - Le depot est un clone superficiel (shallow)
  Cause : la session de travail est clonee en --depth 1 et certaines branches
  distantes n'existaient pas localement.
  Solution : "git fetch origin 'refs/heads/*:refs/remotes/origin/*'" avant
  toute comparaison de branches. Ne pas supposer que l'historique est complet.

INCIDENT 13 - rmdir /s /q sur le mauvais dossier (piege du renommage)
  Contexte : en remplacant le dossier de sortie release\ par jeu\ dans
  build_launcher.bat, un remplacement global a transforme
  'if exist "release" rmdir /s /q "release"' en 'if exist "jeu" rmdir /s /q
  "jeu"' : le script aurait EFFACE jeu\ en entier (launcher.pyw,
  version_url.json, LIS-MOI.txt) a chaque build.
  Solution : la ligne supprime desormais uniquement %JEU%\game (l'ancien
  export), et un controle automatique verifie que toute cible de rmdir /s
  est bien un sous-dossier connu (game, game.install, game.ancien, Library,
  launcher, build).
  LECON : apres un remplacement de chemins dans un .bat, relire CHAQUE ligne
  de suppression. Un "rmdir /s /q" mal cible detruit le travail.

INCIDENT 14 - Pas d'acces reseau direct a GitHub dans le bac a sable
  Symptome : curl vers raw.githubusercontent.com / release-assets.githubusercontent.com
  echoue (SSL_ERROR_SYSCALL, EOF).
  Solution : passer par l'API (gh api) pour verifier qu'un fichier est bien
  publie sur une branche, et tester le launcher avec un serveur HTTP local
  (outils/test_launcher.py) au lieu de taper sur GitHub.

INCIDENT 15 - Le jeu compile affichait tout en magenta (rapporte par l'utilisateur)
  Symptome : capture d'ecran du joueur = collines, batiments et arbres en rose
  fluo ; le HUD, lui, s'affichait normalement.
  Cause    : le HUD est dessine par OnGUI (immediat, shader interne de
  l'interface, toujours present), alors que TOUS les objets 3D recoivent un
  materiau cree par code avec Shader.Find("Standard"). Unity retire de la
  build les shaders integres qu'aucun materiau du projet ne reference (aucun
  materiau ici : tout est cree a l'execution). Dans l'exe, Shader.Find
  renvoyait null -> materiau sans shader -> magenta. Un jeu entier en magenta
  = signe quasi certain de ce probleme, pas d'un probleme de couleur.
  Solution : shader du projet dans Assets/Resources/LVShaders/LVColor.shader
  (Resources = toujours embarque) + chaine de secours, et LOG du shader
  retenu. Pour tout nouveau materiau cree par code : passer par
  ResoudreShader(), jamais par Shader.Find seul.
  ATTENTION : ce bug n'apparait PAS dans l'editeur Unity, seulement dans
  l'exe compile. Toujours tester l'exe, pas seulement Play.

INCIDENT 16 - La camera demarrait sous le terrain (rapporte par l'utilisateur)
  Symptome : "la camera demarre sous le sol" puis remonte, et la souris met un
  temps fou a repondre (meme plainte, meme correctif).
  Cause    : deux bugs independants dans UpdateCamera() et Update() :
             - Quaternion.Euler(cameraPitch = +18) * Vector3.forward place la
               camera SOUS le heros (y negatif) : pour mettre une camera en
               orbite au-dessus, il faut Vector3.back (Unity regarde vers +Z).
             - Input.GetAxis("Mouse X") est lisse, et la sensibilite 0,3
               correspondait a 0,03 degre par pixel au lieu de 0,3.
  Solution : Vector3.back + plafond de securite (0,6 au-dessus du terrain) ;
  GetAxisRaw + sensibilite 3. Voir MAJ 7.

INCIDENT 17 - Les corrections ne partaient pas chez l'utilisateur (le plus sournois)
  Symptome : aucune erreur nulle part, mais le jeu recompile chez l'utilisateur
  restait exactement l'ancien (monde magenta). C'est le genre de piege qu'aucun
  message de log ne signale.
  Cause    : build_launcher.bat commencait par "si le projet existe deja, on ne
  telecharge rien" (pour ne pas ecraser le travail local). Les sources sur ce PC
  n'etaient donc jamais rafraichies, alors que c'est le depot GitHub qui fait
  foi.
  Solution : mise a jour a chaque lancement, avec deux garde-fous : sauvegarde
  de l'ancienne version dans build\sauvegarde_locale\ AVANT de remplacer, et
  le script de fabrication lui-meme n'est jamais ecrase pendant son execution
  (il est pose a cote en .maj). Voir MAJ 9.
  A retenir : apres avoir pousse une correction du jeu, TOUJOURS verifier
  qu'elle arrive jusqu'a l'exe du joueur (et pas seulement dans le depot).

7. REGLES TECHNIQUES A RESPECTER (pour ne pas reproduire les incidents)
================================================================================

  R1. Ne jamais modifier launcher.pyw par regex multi-lignes. Remplacement
      ligne par ligne + compile() de controle (voir incident 7).
  R2. Apres TOUTE modification du launcher, lancer :
        python compilation/outils/test_launcher.py     (31 controles, local)
      et verifier python -m py_compile jeu/launcher.pyw.
  R3. Les .bat sont ecrits en ASCII, sans accents, et doivent passer le
      controleur de blocs/parentheses/labels (incident 8). On ne peut pas les
      executer sous Linux : la relecture automatique est obligatoire.
  R4. Le dossier jeu/ ne contient que launcher.pyw, version_url.json,
      LIS-MOI.txt (plus les fichiers telecharges, ignores par git).
  R5. Le launcher ne telecharge jamais rien venant de compilation/.
  R6. Toute entree du manifeste passe par _safe_local_path : pas de "..",
      pas de chemin absolu, pas de "C:".
  R7. Une archive de jeu publiee ne doit jamais etre ecrasee : son nom
      contient son md5 (LibreVies_jeu_<md5 8 car.>.zip).
  R8. Le jeu ne se met a jour que par une archive complete (game_build) ;
      le contenu de l'archive est place A LA RACINE du zip (pas de dossier
      enveloppe : le launcher remonte quand meme un dossier unique).
  R9. Une panne reseau ne doit jamais bloquer un jeu deja installe : hors
      ligne, le launcher affiche "Hors ligne" mais JOUER marche encore.
  R10. Ne jamais demander de mot de passe, token ou identifiant GitHub : la
      connexion git/gh est deja configuree dans l'environnement.
  R11. Ne pas changer de branche : le travail est publie sur
      arena/01a0b32c-librevies (branche de la session). Pour publier depuis
      une autre branche (main par exemple), utiliser
      outils/definir_url_publication.py --branche main.
  R12. AUCUN materiau 3D ne se cree avec Shader.Find seul : passer par
      ResoudreShader() (incident 15). Tout shader utilise par un materiau cree
      par code doit vivre dans Assets/Resources/ pour survivre a la compilation.
  R13. Une correction de rendu ne se valide QUE dans l'exe compile, jamais dans
      l'editeur Unity (le magenta n'apparaissait pas dans Play, incident 15).
