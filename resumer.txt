03. CIRCUIT GIT -> TÉLÉCHARGEMENT/BUILD -> JEU
--------------------------------------------------------------------------------

CIRCUIT ACTIF :
  IA : modification des sources + tests + resumer.txt + commit + push GitHub.
  Utilisateur Windows : ferme le jeu/launcher -> lance le build -> ouvre le jeu.

Depuis la racine du projet, commande Windows habituelle :
  compilation\build_launcher.bat
Puis :
  jeu\LibreVies.exe

Le build principal :
  - lit la branche configurée et récupère ses sources depuis GitHub ;
  - préserve/sauvegarde les données locales prévues par le workflow, dont les
    coordonnées d’édition, et peut publier les coordonnées avant synchronisation ;
  - synchronise les sources différentiellement par blob SHA et commit immuable,
    pas en mélangeant des téléchargements provenant de HEAD différents ;
  - remet le projet Unity à jour, évitant de recompiler silencieusement l’ancien ;
  - compile le jeu Unity Windows en Mono ;
  - vérifie l’export temporaire AVANT de remplacer le jeu installé ;
  - prépare jeu/game et les informations locales de version ;
  - synchronise jeu/serveur vers la racine web EasyPHP/Apache détectée, sans
    remplacer config.php ni exécuter les SQL ;
  - conserve le créateur autonome compilation/personnage comme outil séparé ;
  - n’a plus de publication finale obligatoire vers jeucompiler.

compilation/build_unity_game.bat existe comme build/diagnostic local :
  il ne télécharge pas les nouvelles sources. Pour une MAJ poussée par l’IA,
  le point d’entrée normal reste build_launcher.bat.

Le synchroniseur actuel télécharge les préfixes compilation/ et jeu/ : il ne
rafraîchit pas automatiquement resumer.txt à la racine du poste Windows.
Pour une passation, lire la version du résumé sur la branche GitHub actuelle,
pas supposer qu’une copie locale ancienne a été mise à jour par le build.

Validation contre le problème « ancien jeu lancé malgré nouveau code » :
  - LibreViesBuild.cs compare la constante des sources, les scripts réellement
    chargés dans l’éditeur (réflexion) et bundleVersion ;
  - l’export vérifie l’assembly Mono, sa version et les méthodes attendues ;
  - le build Unity crée game/version_jeu.json avec version et SHA256 d’assembly ;
  - preparer_jeu_local.py contrôle sources, exécutable, assembly, méthodes,
    marqueur et SHA256 ; --verifier-seulement permet de refuser un export avant
    remplacement ;
  - le préparateur écrit les fichiers locaux de manifeste/état atomiquement
    avec la version réellement compilée, pas une simple étiquette inventée.

mode_local=true signifie que le launcher lance le build vérifié présent dans
jeu/game et ne le remplace plus par d’anciens binaires téléchargés sur HTTP.
Cela NE coupe PAS l’authentification PHP ni les lectures/sauvegardes BDD.
Le launcher reste en deux morceaux : amorce LibreVies.exe + logique launcher.pyw.
Une modification de launcher.pyw n’oblige pas normalement à recompiler l’amorce.
Si un nouvel import doit être embarqué, vérifier compilation/amorce : l’amorce
ancienne ne devine pas un module chargé dynamiquement dans launcher.pyw.

Ne jamais supprimer ni réinitialiser la BDD, Autolog, config.php ou les
coordonnées pour « forcer une MAJ ». Ni le préparateur ni le synchroniseur
serveur ne sont des outils de migration destructive.

06. SCHÉMAS SQL ET INSCRIPTION TRANSACTIONNELLE
--------------------------------------------------------------------------------

Base des scripts : librevies, InnoDB, utf8mb4/utf8mb4_unicode_ci.
Les fichiers SQL actuels décrivent une installation neuve ; CREATE TABLE IF
NOT EXISTS ne transforme pas magiquement une ancienne table incompatible.
Sur une installation neuve, importer membre.sql avant personnage.sql/classement.sql,
puis npc.sql ; aucun de ces schémas ne fournit les profils NPC complets.
Pour une base existante, examiner son schéma et les données avant toute
migration ; faire une sauvegarde. Aucun DROP/recréation/réimport inutile.

membre (jeu/serveur/membre.sql) :
  id INT UNSIGNED AUTO_INCREMENT, PK ;
  pseudo VARCHAR(50) NOT NULL UNIQUE ;
  motdepasse VARCHAR(255) NOT NULL (hash, jamais mot de passe en clair) ;
  email VARCHAR(254) NOT NULL UNIQUE ;
  valider TINYINT(1) NOT NULL DEFAULT 0 ;
  droit TINYINT UNSIGNED NOT NULL DEFAULT 0.

personnage (jeu/serveur/personnage.sql) :
  id INT UNSIGNED, PK et FK vers membre.id, cascades update/delete ;
  default TINYINT(1) NOT NULL DEFAULT 1 ;
  sexe ENUM('homme','femme') NULL ;
  13 colonnes DECIMAL(10,4) NULL :
    tete, yeux, nez, bouche, oreilles, seins, volume, hanche, ventre,
    largeur_bras, longueur_bras, hauteur_jambe, pieds ;
  teinte_peau VARCHAR(32) NULL ;
  coiffure, chaussures, chapeau, tenue VARCHAR(100) NULL ;
  objets TEXT NULL.
  Toutes les colonnes autres que id/default restent NULL à l’inscription.

classement (jeu/serveur/classement.sql) :
  id INT UNSIGNED, PK/FK vers membre.id ;
  experience BIGINT UNSIGNED NOT NULL DEFAULT 0 ;
  chasse BIGINT UNSIGNED NOT NULL DEFAULT 0 ;
  territoire BIGINT UNSIGNED NOT NULL DEFAULT 0.
  Le script complète seulement les membres sans classement via INSERT IGNORE
  et LEFT JOIN ; il ne remet pas à zéro les scores existants.

npc (jeu/serveur/npc.sql) :
  id VARCHAR(100), PK (texte comme 'maire') ;
  exactement les mêmes champs de personnalisation que personnage ;
  AUCUNE colonne default, AUCUNE FK vers membre ;
  champs de personnalisation NULL tant que non renseignés.
  21 colonnes au total, ID compris ; personnage en a 22 avec default.
  Ni métier, ville, coordonnées ni accessoires runtime ne sont stockés dans
  les colonnes de personnalisation ajoutées ici.

INSCRIPTION ACTUELLE : UNE TRANSACTION POUR LES TROIS LIGNES
  1) INSERT membre avec valider=0 et droit=0.
  2) Récupération du nouvel ID canonique de membre.
  3) INSERT personnage au même ID, default=1, tous les autres champs NULL.
  4) INSERT classement au même ID, experience=0, chasse=0, territoire=0.
  5) COMMIT seulement si tout réussit, sinon ROLLBACK.

Les doublons pseudo/email sont vérifiés avec des requêtes SQL préparées et
la collation de MySQL. Le traitement 1062 ne doit appeler « doublon de membre »
que ce cas précis, pas masquer une erreur d’insertion personnage/classement.
La demande initiale sans classement a été remplacée par la demande explicite
ultérieure d’ajouter cette table et les trois scores à 0.

Email : aucun envoi et aucun flux de validation email implémentés actuellement.
valider=0 est normal et permet la connexion. Ne pas activer par défaut une
option require_email_validation qui bloquerait les comptes de développement.

Le panneau « Votre classement » remplace l’inscription après connexion, avec
Experience/Chasse/Territoire. ATTENTION : la table et son initialisation sont
faites, mais le launcher n’est PAS déjà un classement live complet : ses pages
publiques affichent encore « Aucune donnee pour le moment ». Pas de nouveau
contrat API de classement temps réel livré dans les derniers changements.

07. IDENTITÉ, API, SESSIONS ET AUTOLOG CHIFFRÉ
--------------------------------------------------------------------------------

Le launcher ne fait jamais de SQL. Les comptes passent par api.php, qui vérifie
la BDD avec PDO et password_verify. Les bcrypt existants restent valables ;
les nouveaux hashes utilisent Argon2id si disponible, sinon le mécanisme fort
supporté par PHP. Pas de conversion des mots de passe existants en clair.

Réponse type API : ok, message et données métier (membre/personnage/npcs/session
selon action). Formulaire POST classique ou JSON accepté côté API ; Unity
transporte le profil en JSON dans un POST formulaire. JSON de TRANSPORT ne
signifie pas colonnes JSON supplémentaires en BDD.

Actions utiles :
  health               diagnostic serveur/BDD non destructif ;
  register             création transactionnelle membre/personnage/classement ;
  registration_status  vérification après inscription via pseudo + email ;
  login                vérifie pseudo/password et fournit session + identité ;
  get_character        session_token -> identité et profil joueur ;
  save_character       session_token + personnage -> profil enregistré/relu ;
  get_npcs             session_token -> les six profils humains ;
  save_npc             session_token + npc_id + personnage, droit BDD EXACTEMENT 1.

Règle de sécurité : ID, pseudo ou droit envoyés par un client ne sont JAMAIS
une preuve d’identité/permission. PHP relit le membre depuis la session et la
BDD à chaque requête authentifiée. Le pseudo Unity vient de cette identité,
pas d’un champ libre local. Modifier le client ne confère pas le droit admin.

Session :
  - jeton opaque de 32 octets cryptographiques, 64 caractères hex, 256 bits ;
  - expiration 24 h, renouvelé à chaque connexion ;
  - sessions PHP strictes, sans cookies ni jeton dans une URL ;
  - jeton seulement en RAM du launcher puis dans l’environnement du processus
    du jeu (LIBREVIES_SESSION_TOKEN, URL via LIBREVIES_API_URL) ;
  - Unity efface la variable jeton de son environnement après lecture et garde
    la session en RAM ; le singleton compte survit à un rechargement de scène ;
  - pas de fichier de session, pas de jeton dans Autolog/manifeste/logs.

Génération (securite.php) : random_bytes sur PHP moderne ; compatibilité ancienne
par OpenSSL fort, puis /dev/urandom Unix ou Windows .NET via PowerShell si
proc_open est autorisé. L’ancien poste PHP 5.6 sans OpenSSL bloquait la création
sécurisée des sessions ; 0062706 a ajouté le fallback Windows cryptographique.
JAMAIS rand/mt_rand/uniqid/microtime comme générateur de jetons. Si aucune source
forte n’est possible, refuser proprement plutôt que fabriquer un jeton faible.

Statuts :
  400 : profil/valeur/ID refusé ;
  401 : session absente/expirée/invalide (Unity réinitialise l’identité) ;
  403 : sauvegarde NPC interdite (Unity retire le droit admin local) ;
  409 : doublon de compte ou profil NPC absent/incomplet selon action ;
  500/503 : incident BDD/serveur (consulter le log, pas réinitialiser les tables).

AUTOLOG :
  - jeu/autolog.dat dans GAME_DIR, chiffré Windows DPAPI ;
  - le JSON historique en clair est migré puis supprimé ;
  - décocher Autolog efface les deux formats ;
  - aucune donnée Autolog dans version_url.json ou sur GitHub ;
  - jamais de mot de passe ni jeton journalisé ;
  - ne pas revenir à « simple encodage » base64 ou à du JSON plaintext.

Inscription et UI launcher : une requête register vérifie les doublons et
insère ; ensuite registration_status vérifie jusqu’à dix fois, environ une
seconde entre essais. On ne rajoute pas un appel de précontrôle qui bloquerait
le retour UI. Les résultats passent par une file interne et sont traités dans
le thread principal Tk, pas dans le worker réseau. L’import queue ajouté puis
retiré évite de dépendre d’une nouvelle amorce embarquant ce module.

Le bouton Jouer du launcher exige une connexion réussie ; mode local ne signifie
pas compte invité ni droit administrateur sans identité.

Après connexion : Bonjour <pseudo>, champs/titres Pseudo/Connexion/Mot de passe
masqués et inscription remplacée par le panneau de classement ; Autolog reste
visible. Une erreur doit revenir clairement dans la barre, pas rester figée.
Les redémarrages PyInstaller onefile ont été isolés avec nouvelle extraction/
PYINSTALLER_RESET_ENVIRONMENT=1 et fermeture des handles, pour ne pas dépendre
d’un ancien dossier temporaire _MEI déjà supprimé ou verrouillé.

08. PERSONNAGE JOUEUR ET CRÉATEUR CHEZ LE NPC ESTHÉTIQUE
--------------------------------------------------------------------------------

Le profil est chargé depuis PHP après authentification. default=1 conserve le
personnage de base. Le joueur doit aller au NPC Esthétique pour personnaliser
et valider ; ce panel a été retiré du parcours ADMIN joueur.

Tous les réglages utilisent la même ligne personnage.id = membre.id.
VALIDER / ENREGISTRER -> save_character -> transaction et relecture BDD ->
application du profil serveur confirmé avec default=0. Annuler/fermer n’écrit
rien. Un refus réseau/serveur garde le brouillon et l’avatar actuel.

Mapping complet des 13 sliders :
  SQL                 Createur
  tete                headShape
  yeux                eyesShape
  nez                 noseShape
  bouche              mouthShape
  oreilles            earsShape
  seins               chestShape
  volume              legThickness
  hanche              hipShape
  ventre              belly
  largeur_bras        armThickness
  longueur_bras       armLength
  hauteur_jambe       legLength
  pieds               feetSize

Valeurs internes 0 à 5, affichage du panel 0 à 500, quatre décimales SQL.
Ne pas remplacer ces 13 colonnes par sliders JSON ni ajouter cree_le/modifie_le.

Choix persistés par ID du catalogue (pas par indice du dropdown) :
  sexe homme/femme ; peau IDs 0..6 ; coiffures catalogue MakeHuman ;
  tenues homme/femme ; chapeau NULL ou fedora01 ;
  chaussures NULL ou shoes01..shoes06.
« Aucun » doit rester NULL pour chapeau/chaussures. objets TEXT est préservé,
le créateur ne l’écrase pas sous prétexte qu’il ne le gère pas encore.

AdminHumanCreator.ApplyTo sert maintenant aussi à reconstruire un humain sur
un root existant. Le créateur autonome dans compilation/personnage est un autre
outil : modifier seulement celui-ci ne mettrait pas à jour le salon en jeu.

09. NPC HUMAINS, PROFILS PERSISTANTS ET RECONSTRUCTION MAKEHUMAN
--------------------------------------------------------------------------------

Six ID contractuels actuels :
  maire, forgeron, marchand, esthetique, garde_nord, garde_sud.

Les profils ont été tirés aléatoirement une fois et enregistrés en BDD, puis
get_npcs les charge/reconstruit avec le même créateur MakeHuman que le joueur.
Ils ne sont PAS rerandomisés à chaque connexion. Les tables ne doivent pas
être réensemencées à chaque build/import/API. Les anciennes formes primitives
ne sont plus le rendu attendu des humains du village.

Historique du seed : le SQL ponctuel remplir_npc.sql existait dans ac40541,
puis a été retiré du paquet serveur dans 386bb30 à la demande de l’utilisateur.
Il est maintenant seulement sous :
  compilation/outils/fixtures/npc_profiles_fixture.sql
C’est une fixture hors serveur, jamais importée automatiquement. Une table npc
vide/incomplète n’est pas automatiquement remplie par le build actuel ; traiter
ce cas explicitement et conserver les profils déjà existants.

Le DTO LibreViesNpc porte l’ID texte et les réglages. Son adaptateur de profil
utilise un default=0 EN MÉMOIRE pour le créateur ; ce n’est pas une colonne
ajoutée à npc ni une relation vers un joueur.

Reconstruction :
  - conserver le root, la position/rotation, le métier, les dialogues et gameplay ;
  - masquer/remplacer les visuels primitifs sans supprimer les contrôles utiles ;
  - détacher les accessoires de l’ancien squelette AVANT de détruire son root ;
  - reconstruire mesh/rig MakeHuman et rattacher les accessoires au nouveau rig ;
  - garder marteau, équipement et hallebarde au bon personnage ;
  - ne pas modifier le profil/ID du joueur pendant l’édition d’un NPC.

FindBone : le wrapper AppliedBone existait mais la classe imbriquée HumanPreview
n’avait pas FindBone, d’où CS1061. 386bb30 ajoute public FindBone dans CETTE
classe, avec vérifications null/bornes et TryGetValue. Ne pas « réparer » en
ajoutant seulement un wrapper au mauvais niveau de classe.

La capture utilisateur du jeu 0.5.85 confirme que les humains et le pseudo
s’affichaient réellement. Elle ne prouve pas à elle seule toutes les opérations
BDD, et montrait la mauvaise prise des armes des gardes.

13. INCIDENTS : SYMPTÔMES, CAUSES, SOLUTIONS ET FAUSSES PISTES
--------------------------------------------------------------------------------

1) Jeu magenta / monde invisible / caméra sous le sol au début.
   Causes : shaders non embarqués/compatibilité et caméra/rendu incorrects.
   Solution : shaders de secours Resources avec leurs .meta, corrections caméra
   et démarrage instrumenté. Voir l’archive ; ne pas supprimer ces ressources.

2) Gel au chargement du village.
   Cause réelle d’un incident initial : boucle infinie de génération de clôture.
   Solution : correction de boucle et étapes de démarrage loguées. Ne pas
   attribuer systématiquement un gel à un manque de RAM ou au téléchargement.

3) Build qui compile l’ancien jeu malgré une MAJ.
   Causes multiples rencontrées : sources non rafraîchies, mauvaise racine de
   build/publication, scripts Unity chargés obsolètes, manifeste stale et ancien
   binaire retéléchargé par le launcher.
   Preuve : assembly publiée 0.5.79 ne contenait pas les méthodes compte/pseudo.
   Solution actuelle : sources différentielles cohérentes, contrôles source/
   scripts/bundleVersion, version_jeu.json/SHA256, export contrôlé avant remplacement,
   mode local et aucun écrasement par des binaires HTTP anciens.
   Mauvaise solution : renommer juste le manifeste ou recommencer jeucompiler.

4) Inscription insérée mais launcher bloqué / retour UI manquant.
   Causes rencontrées : réponse JSON PHP incorrecte, ancienne API, seconde
   requête de précontrôle, verification post-INSERT et thread Tk incorrect.
   Solution : réponse PHP propre, register unique, polling status pseudo+email,
   logs précis et traitement des callbacks dans le thread principal.

5) Doublons affichés incorrectement ou erreur SQL cachée.
   Solution : vérifier les deux champs via la collation SQL, messages explicites,
   code 409 ; ne traiter 1062 comme doublon membre que pour l’INSERT membre.
   Rollback transactionnel si personnage/classement échoue.

6) Redémarrage PyInstaller échoue / erreur de dossier temporaire onefile.
   Causes : réutilisation _MEI supprimé, environnement et handles hérités.
   Plusieurs essais CMD/délai ont été insuffisants. Solution retenue : nouveau
   bootloader/environnement PYINSTALLER_RESET_ENVIRONMENT=1, handles fermés,
   conserver le comportement utilisateur attendu, pas masquer l’erreur.

7) Import queue absent dans l’amorce existante.
   Solution finale : supprimer cette dépendance du launcher au profit d’une
   file interne ; éviter d’imposer une nouvelle amorce pour ce seul correctif.

8) Autolog stocké en clair / persistant alors que décoché.
   Solution : Windows DPAPI, migration/suppression du JSON ancien et suppression
   des deux formats si décoché. Ne pas stocker de secrets dans un manifeste.

9) Connexion/session impossible sur ancien PHP sans OpenSSL.
   Cause : aucune source cryptographique utilisable dans le premier chemin.
   Solution 0062706 : fallback Windows .NET PowerShell fort sous PHP 5.6 ;
   PHP 8.3 utilise random_bytes. Ne jamais remplacer par un RNG faible.

10) Pseudo absent en jeu alors que le code et le compte semblaient corrects.
    Cause prouvée : binaire 0.5.79 sans fonctionnalités récentes lancé réellement.
    Solution : vérifier/installer le bon build, puis reprendre le pseudo canonique
    PHP ; pas inventer un pseudo de fallback visible ni écrire une autre identité.

11) Texte Entrepôt apparaît sur/à travers Esthétique.
    Cause : taille du texte et gestion de profondeur/occlusion.
    Solution : ajustement aux localBounds du panneau, shader LVFacadeText
    ZTest LEqual et raycast ; respecter la profondeur du monde.

12) Push refusé pendant que l’utilisateur enregistre les coordonnées ou supprime
    un dossier.
    Cause : branche distante a avancé. Solution : fetch, relecture du nouveau
    parent et réapplication des SEULS fichiers concernés ; conserver les commits
    coordonnées et la suppression jeucompiler. Un index temporaire/commit-tree
    a déjà été utilisé pour éviter stash/restauration massive d’un worktree sale.
    Ne pas force-push ni ramener une ancienne arborescence supprimée.

13) CS1061 HumanPreview.FindBone — ÉCHEC RÉEL DE COMPILATION.
    ac40541 avait ajouté l’appel mais pas la méthode dans HumanPreview.
    386bb30 corrige réellement cette omission. Le scanner tree-sitter et les
    tests de contrat n’avaient pas détecté l’erreur sémantique C#.
    Le log contenait aussi des avertissements licence Unity : la licence
    Personal Unlimited avait été résolue, ce n’était pas la cause du return 1.
    Ne pas conseiller une nouvelle licence/install Unity pour corriger CS1061.

================================================================================
3. COMMENT FONCTIONNE LE LAUNCHER (jeu/launcher.pyw, version 4.1.0)
================================================================================

3.0 AMORCE ET CODE (a comprendre avant tout le reste, MAJ 12)
  Le launcher est en DEUX morceaux :
    - jeu\LibreVies.exe : une AMORCE de ~200 lignes, compilee depuis
      compilation\amorce\amorce_launcher.py. Elle ne fait que trois choses :
      recuperer launcher.pyw a cote d'elle (au premier lancement elle recopie
      la copie que PyInstaller a embarquee avec --add-data), l'executer comme
      un programme, et ecrire journal_launcher.txt + une boite d'alerte si le
      launcher plante.
    - jeu\launcher.pyw : TOUT le launcher (interface, telechargements, mise a
      jour). Il est publie avec son hash dans version_url.json.
  POURQUOI : quand on change une phrase du launcher, seul launcher.pyw change ;
  le hash change, le launcher le telecharge et redemarre tout seul. Il n'y a
  donc PLUS JAMAIS de PyInstaller a relancer pour modifier le launcher. Seule
  une modification de l'amorce elle-meme demanderait de recompiler l'exe.

3.1 Suite : launcher.pyw est un fichier Python unique de ~650 Ko : ~1150 lignes + les
images (banniere, icone, ICO) integrees en base64. Il n'a besoin d'AUCUNE
bibliotheque externe : tkinter (livre avec Python) et, si present, Pillow
(facultatif : sans lui, les PNG integres passent par tk.PhotoImage).

3.2 Au lancement (1er passage)
  - GAME_DIR = dossier du .exe (ou du .pyw en developpement).
  - Il lit jeu/version_url.json recopie a cote de lui. S'il n'existe pas, il
    utilise DEFAULT_RAW_URL ecrit en dur (valeur de secours).
  - Il lit le manifeste distant (raw_url) : URL GitHub "raw".

3.3 Mise a jour des petits fichiers (cle "files" du manifeste)
  - Uniquement des fichiers TEXTE (md5 calcule sur le contenu normalise LF/CRLF).
  - Quand on developpe avec launcher.pyw, les entrees launcher.pyw et
    LibreVies.exe sont ignorees (sinon on ecraserait ses propres sources).
  - Les chemins sont valides par _safe_local_path() : refus des chemins
    absolus, des lecteurs Windows (C:) et de tout "..". Un manifeste corrompu
    ne peut donc pas ecrire hors du dossier du launcher.
  - Le launcher compile (LibreVies.exe) ne peut pas se remplacer pendant qu'il
    tourne : il depose .new puis un .cmd remplace le fichier apres fermeture et
    relance le launcher.
  - launcher.pyw (le CODE du launcher, celui qui est en train de tourner) fait
    partie de cette liste : si son hash change, il est telecharge puis le
    launcher se contente de REDEMARRER (l'amorce relit le fichier a chaque
    lancement). C'est ce qui rend toute recompilation inutile.

3.4 Mise a jour du JEU COMPLET (cle "game_build" du manifeste)
  C'est le coeur de la distribution. Le jeu n'est PAS telecharge fichier par
  fichier : il arrive en UNE SEULE archive .zip.

    {
      "game_build": {
        "moteur": "unity",
        "version": "0.4.0",
        "dossier": "game",           <- ou l'archive est installee
        "exe": "LibreViesGame.exe",  <- lance par le bouton JOUER
        "url": "https://github.com/.../releases/download/derniere/LibreVies_jeu_xxxx.zip",
        "size": 39269570,
        "hash": "md5 de l'archive"
      }
    }

  Deroulement de installer_build_jeu() :
    1. telechargement dans jeu.download.part avec en-tete HTTP Range si un
       fichier partiel existe (reprise), verif que le serveur repond bien 206
       sinon on repart de zero, barre de progression en Mo ;
    2. controle de la TAILLE puis du MD5 annonces par le manifeste. Si l'un des
       deux est faux : l'archive est effacee et l'installation existante reste
       intacte (le joueur peut toujours jouer) ;
    3. extraction dans game.install\ avec protection contre les archives
       piegees (tout chemin contenant "..", absolu ou avec "C:" est refuse) ;
    4. si l'archive contient un unique dossier racine, il est "remonte" ;
    5. recherche de l'executable (LibreViesGame.exe) ;
    6. remplacement ATOMIQUE : l'ancienne installation devient game.ancien\,
       la nouvelle game\, puis game.ancien\ est supprime. En cas d'echec, on
       remet l'ancienne en place ;
    7. etat enregistre dans etat_jeu.json (hash, version, exe, date) ;
    8. archive supprimee.

  build_a_installer() decide s'il faut (re)telecharger :
    - pas de hash dans le manifeste -> "aucune compilation Unity publiee"
      (message affiche au joueur, bouton JOUER grise) ;
    - hash different de etat_jeu.json -> "nouvelle compilation disponible" ;
    - hash identique mais jeu absent/casse -> "fichiers du jeu a reparer" ;
    - sinon -> "jeu a jour".

3.5 Le deroulement attendu par l'utilisateur (sa description, mot pour mot)
  "Je le mets en route, il telecharge le fichier version sur GitHub, il le
   compare a celui en local : si des hash changent, il y a eu une maj sur tel
   ou tel fichier ; dans ce cas il telecharge le ou les nouveaux fichiers,
   remplace les vieux en local par les nouveaux, pareil pour le fichier
   version, et redemarre le launcher qui va a nouveau verifier : si tout
   correspond, il rend le bouton JOUER disponible et on demarre le jeu."
  C'EST EXACTEMENT CE QUE FAIT LE LAUNCHER (voir 3.1 a 3.4). Une seule nuance,
  qui compte pour ne pas se tromper :
    - les PETITS FICHIERS (launcher.pyw, textes, exe du launcher) arrivent un
      par un, par hash, exactement comme il le decrit ;
    - le JEU lui-meme (le dossier game/) arrive en UNE SEULE archive .zip
      publiee dans la release GitHub, controlee par son md5 (cle game_build).
      C'est voulu : des milliers de fichiers Unity un par un seraient beaucoup
      plus lents et fragiles.
  CONSEQUENCE A DIRE A L'UTILISATEUR : il n'a plus jamais besoin de recompiler
  le LAUNCHER (MAJ 12), mais quelqu'un doit compiler le JEU quand le code du
  jeu change : seul son PC a Unity. Donc quand une correction touche
  LibreViesGame.cs, il lance build_launcher.bat une fois (ou seulement l'export
  Unity) puis publie ; tous les launchers, y compris le sien, se mettent a jour
  tout seuls ensuite. La seule facon de supprimer aussi cette etape serait une
  compilation automatique sur GitHub (GitHub Actions + licence Unity) : a
  proposer seulement s'il le demande.

3.6 Etat vide du manifeste (IMPORTANT pour comprendre l'etat actuel)
  Aujourd'hui jeu/version_url.json a "game_build": {} et "files": {}.
  Cela veut dire : AUCUNE compilation n'a encore ete publiee. Le launcher
  affiche donc "aucune compilation Unity publiee" et le bouton JOUER reste
  grise. C'est voulu : c'est la premiere publication (section 4) qui remplit
  ce bloc, et tout devient automatique ensuite.

4. PUBLIER UNE MISE A JOUR (procedure normale, cote auteur, sous Windows)
================================================================================

  1. compilation\build_launcher.bat   (double-clic)
     Il telecharge ce qui manque (voir section 6) puis COMPILE et DEPOSE tout
     dans le dossier jeu\ :
        jeu\LibreVies.exe   <- LE fichier a donner au joueur
        jeu\game\           <- le jeu a publier
     A la fin il demande : "Publier cette compilation maintenant ? [O/N]"

  2. Repondre O  -> il enchaine sur outils\publier_jeu.bat, qui :
       - rassemble jeu\game en UNE archive LibreVies_jeu_<md5>.zip ;
       - l'envoie dans la release GitHub "derniere" (gh release upload) ;
       - ecrit url/size/hash/moteur/exe/version dans jeu/version_url.json ;
       - publie aussi jeu\LibreVies.exe (cle "files"/"LibreVies.exe")
         pour que les launchers deja installes se mettent a jour ;
       - note l'installation locale dans jeu\etat_jeu.json : le launcher d'ici
         affiche "jeu a jour" sans retelecharger ce qui vient d'etre compile ;
       - avec --pousser : git add/commit/push du manifeste.

  3. Les joueurs recoivent la mise a jour au prochain lancement.

  Le nom de l'archive contient son md5 : une nouvelle publication ne remplace
  jamais l'archive sous les pieds d'un joueur en train de telecharger.
  Sans gh installe, publier_jeu.py cree quand meme l'archive et le manifeste
  et affiche l'URL exacte ou deposer le .zip a la main.

  MAJ 7 - Monde magenta, camera sous le sol, souris molle : corriges
    C'est la MAJ qui repond aux 3 bugs signales par l'utilisateur avec la
    capture d'ecran du monde entier en rose fluo (upload image-1.png), puis
    "fait moi pareil mais en unity" (reprendre le jeu de la branche de
    reference arena/01a09a4d-librevies).

    a) MONDE MAGENTA. Cause : le jeu cree TOUS ses materiaux par code avec
       Shader.Find("Standard"). Unity supprime de la build les shaders
       integres qu'aucun materiau du projet ne reference ; dans l'exe compile
       Shader.Find renvoyait donc null, et Unity affiche en magenta tout objet
       dont le materiau n'a pas de shader valide. Correctif : nouveau shader
       du projet Assets/Resources/LVShaders/LVColor.shader (tout ce qui est
       dans un dossier Resources est TOUJOURS embarque dans la build) et
       chaine de secours dans ResoudreShader() :
         Standard -> Resources LVColor -> Unlit/Color -> Sprites/Default ->
         UI/Default -> (echec total : Debug.LogError + materiau null)
       Le shader retenu est ecrit dans la console (Debug.Log) pour diagnostiquer
       en une ligne chez le joueur. Les .meta des deux shaders sont ecrits a la
       main avec des GUID fixes (a1b2c3d4e5f60718293a4b5c6d7e8f90 et
       0f1e2d3c4b5a69788796a5b4c3d2e1f0) : Unity les importe tels quels.

    b) CAMERA QUI DEMARRE SOUS LE SOL. Cause : la camera orbitait avec
       Quaternion.Euler(cameraPitch = +18) * Vector3.forward, ce qui envoie la
       camera VERS LE BAS (a l'ouverture : y = -0,85, donc sous le village,
       d'ou l'ecran qui part du sol et remonte). Correctif : Vector3.back
       (la camera se place derriere ET AU-DESSUS du heros) + filet de securite
       identique a celui de la reference : jamais a moins de 0,6 au-dessus de
       TerrainHeight(x, z). La vue 1re personne regarde desormais dans l'axe
       du pitch (Quaternion.Euler(-pitch, yaw, 0)) au lieu de la rotation du
       personnage.

    c) SOURIS "LONGUE A LA DETENTE". Deux causes cumulees : Input.GetAxis
       lisse les mouvements, et la sensibilite valait 0,3 alors que la
       reference utilise 0,3 degre par pixel, soit 3 avec le facteur 0,1 que
       Unity applique a Mouse X/Y (10 fois trop lent). Correctif :
       Input.GetAxisRaw + sensibilite 3, reglable avec [ et ], memorisee dans
       PlayerPrefs ("cameraSensitivity") et affichee dans le panneau Options.
       Le clic droit pour tourner la camera est conserve (comme la reference).

    d) RENDU ALIGNE sur la reference : ciel bleu vif avec horizon chaud
       (Skybox/Procedural regle sur _SkyTint 0.30/0.46/0.78, _GroundColor
       0.45/0.50/0.26, _Exposure 1.35 ; repli sur le shader du projet
       Assets/Resources/LVShaders/LVSky.shader), soleil energie 1,3, couleur
       (1 ; 0,90 ; 0,74), rotation (52, -32, 0), lumiere ambiante tricolore et
       brouillard adouci (densite 0,0022), champ de vision 55 (celui de la
       Camera3D de la reference, au lieu de 65).

    son journal s'arretait sur :
        [LV] 0,41 s  debut : cloture et portails
    ...sans jamais ecrire "fin : cloture et portails". Le gel etait donc dans
    CreateFence(), et nulle part ailleurs.
    CAUSE (incident 19) : la methode declarait une variable locale nommee
    'portails' -- le meme nom que le CHAMP 'portails' de la classe. Ce champ
    garde la position des portails pour les gardes (un garde par portail).
    Deux consequences :
      1. la liste des intervalles d'angle masquait le champ : CreateGuards()
         n'aurait recu AUCUN portail (donc aucun garde) ;
      2. la boucle de construction des portails faisait
         'for (int g = 0; g < portails.Count; g++)' en AJOUTANT dans
         'portails' : la liste grandissait a chaque tour, la condition restait
         vraie -> boucle infinie. Unity ne dit rien, aucun journal, aucune
         erreur : la fenetre reste figee. L'utilisateur a du la fermer a la
         main (le journal s'arrete net, sans arret propre).
    CORRECTION : la liste des intervalles s'appelle maintenant 'intervalles' et
    ne masque plus rien ; les positions sont bien ajoutees au CHAMP 'portails'.
    Verifie par simulation : 2 portails (nord 6,35 m a (0,9 ; 26) et sud
    6,58 m a (2,2 ; -25,9)), 88 poteaux sur 96, donc 2 gardes (un par portail).
    PROTECTIONS AJOUTEES (pour que cette faute ne revienne jamais) :
      - verifier_cs_syntaxe.py signale maintenant les BOUCLES INFINIES :
        toute boucle 'for (... ; i < X.Count ; ...)' qui contient 'X.Add(' ou
        'X.Insert(' est une erreur bloquante. Teste sur une copie ou le bug a
        ete reintroduit volontairement : detecte.
      - il signale aussi les variables locales qui MASQUENT un champ de la
        classe principale (meme incident), en ignorant les classes imbriquees
        (Maillage, EnemyState...) ou le masquage est sans consequence.
      - une variable locale 'avancement' d'UpdateEffects a ete renommee
        'progression' pour la meme raison.
    - A FAIRE COTE UTILISATEUR : recompiler (build_launcher.bat) et relancer.
      C'est la premiere fois depuis la MAJ 8 que le jeu doit demarrer en entier.


================================================================================
6. JOURNAL DES PROBLEMES RENCONTRES ET DE LEURS SOLUTIONS
   (a lire avant de "corriger" quoi que ce soit : la plupart sont des pieges)
================================================================================

INCIDENT 1 - Le depot melangeait deux moteurs (l'ancien + Unity)
  Symptome : plusieurs branches avec des versions differentes du jeu ; le
  manifeste pointait un coup vers l'ancien moteur, un coup vers Unity.
  Cause    : historique du projet (portage de l'ancien moteur vers Unity par
  une autre IA) ; la branche de travail choisie par l'utilisateur est celle
  d'Unity.
  Solution : decision de l'utilisateur = UNITY UNIQUEMENT. Toutes les traces
  de l'ancien moteur ont ete retirees du depot (manifeste, launcher, outils,
  commentaires).
  Reste a faire : 3 archives de l'ancien moteur (~117 Mo) trainent dans la release
  GitHub "derniere" (LibreVies_Windows*.zip). Plus rien ne pointe dessus.
  Attente de la decision de l'utilisateur pour les supprimer.

INCIDENT 2 - Le modele "un fichier par fichier" ne tenait pas
  Symptome : package.files devait lister chaque fichier de la build (dll,
  dossiers *_Data, ressources...) avec son md5. Des centaines d'entrees a
  regenerer a chaque build, et une coupure de connexion obligeait a tout
  reprendre.
  Solution : le jeu est publie en UNE archive .zip identifiee par son md5.
  make_package_manifest.py (qui generait ce manifeste par fichier) a ete
  supprime ; c'est publier_jeu.py qui remplit game_build.

INCIDENT 3 - L'etape "icone" du build echouait TOUJOURS
  Symptome : le build s'arretait avec "ERREUR : impossible de creer icon.ico".
  Cause : le script utilisait python -c "... spec_from_file_location('lv',
  'launcher.pyw') ...". spec_from_file_location ne reconnait pas l'extension
  .pyw : il renvoie None et module_from_spec plante (AttributeError).
  Solution : nouvel outil compilation/outils/creer_icone.py qui utilise
  importlib.machinery.SourceFileLoader (qui charge n'importe quelle extension),
  verifie l'en-tete du .ico et la taille. Si l'icone echoue, le build CONTINUE
  sans icone au lieu de s'arreter.

INCIDENT 4 - Le telechargement du projet ecrasait des fichiers locaux (risque)
  Symptome : aucun, mais le risque etait reel : si on ecrase le dossier de
  l'auteur avec l'archive GitHub, on perd son travail en cours.
  Solution : robocopy /E /XC /XN /XO (copie uniquement ce qui est ABSENT).
  Verifie par simulation : les fichiers deja presents sont intacts.

INCIDENT 5 - PyInstaller ne trouvait pas l'icone (rapporte par l'utilisateur)
  Symptome exact :
    FileNotFoundError: Icon input file
    ...\compilation\build\icon.ico not found
    (le .ico existait pourtant dans ...\compilation\icon.ico)
  Cause : PyInstaller resout un chemin d'icone RELATIF au dossier du fichier
  .spec (--specpath, donc build\), pas au dossier courant.
  Solution : passage du chemin ABSOLU et entre guillemets:
      set "ICONE_ARG=--icon="%ROOT%icon.ico""
  Le double guillemet externe de set "VAR=..." et les guillemets internes
  sont volontaires : le dossier de l'utilisateur contient des espaces
  (C:\Users\Dragonus\Desktop\Jeu\LibreVies\unity2\compilation\...).

INCIDENT 6 - LibreVies.exe aspirait pygame/numpy
  Symptome (visible dans le journal du build) : PyInstaller analysait
  hook-pygame/hook-numpy/hook-PIL/hook-psutil et "pygame 2.6.1 ... Hello from
  the pygame community" s'affichait pendant le build.
  Cause : ces paquets sont installes dans le Python de l'auteur ; un fichier
  .pth de site-packages provoque leur import pendant l'analyse, et PyInstaller
  embarque tout ce qu'il a vu -> executable inutilement enorme.
  Solution : --exclude-module pygame --exclude-module numpy --exclude-module
  psutil --exclude-module setuptools --exclude-module pip (aucun n'est utilise
  par le launcher). Pillow reste inclus : il sert a redimensionner la banniere.

INCIDENT 7 - Un de mes outils a corrompu le launcher (le plus grave)
  Symptome : IndentationError: unexpected indent, launcher.pyw line 88.
  Cause : definir_url_publication.py (1re version) remplacait DEFAULT_RAW_URL
  avec une REGEX multi-lignes trop gourmande : elle a avale le bloc
  "def start_update" qui suivait.
  Solution : remplacement LIGNE PAR LIGNE (on part de la ligne qui commence
  par "DEFAULT_RAW_URL" et on compte les parentheses), plus deux garde-fous :
  compile() sur le resultat et comparaison du nombre de lignes. Rien n'est
  ecrit si l'un des deux echoue. Le launcher a ete reconstruit depuis git.
  LECON : ne jamais modifier launcher.pyw avec une regex multi-lignes ; et
  toujours verifier avec py_compile/compile() avant/arriere.

INCIDENT 8 - cmd.exe : parentheses dans un echo a l'interieur d'un bloc
  Symptome : erreur de syntaxe du .bat, ou texte tronque.
  Cause : dans un bloc ( ... ), une parenthese non echappee ferme le bloc.
  Solution : ^( et ^) partout dans les echo places dans un bloc.
  Comme le developpement se fait sous Linux (pas de cmd.exe), un CONTROLEUR
  Python verifie chaque .bat : equilibre des blocs, parentheses en milieu de
  ligne, guillemets impairs, et presence des etiquettes (labels) appelees.
  Ce controle a trouve une vraie faute : une ligne "echo ... l''acces ..."
  (double apostrophe) corrigee.

INCIDENT 9 - choix [O/N] avec une logique inversee
  Cause : errorlevel de choice = INDEX de la touche (1 pour O, 2 pour N), pas
  un code d'erreur ; "if errorlevel 1" est donc vrai dans les deux cas.
  Solution : "if errorlevel 2 goto :fin" puis "if not errorlevel 1 goto :fin"
  (seul un O explicite lance la publication).

INCIDENT 10 - Tester le launcher sans tkinter (bac a sable Linux)
  Cause : tkinter n'est pas installable/installe dans l'environnement de
  developpement de l'IA.
  Solution : la recette (outils/test_launcher.py) injecte un faux module
  tkinter dans sys.modules et charge le launcher avec SourceFileLoader. On
  teste ainsi TOUTE la logique (telechargement, md5, installation, reprise,
  securite) sans interface graphique.

INCIDENT 11 - Chez le joueur : ecriture impossible a cote du launcher
  Cause : si LibreVies.exe est dans C:\Program Files, Windows interdit
  l'ecriture et le jeu ne peut pas s'installer.
  Solution : LIS-MOI.txt demande de mettre LibreVies.exe sur le Bureau, dans
  Documents ou sur une cle USB.

INCIDENT 12 - Le depot est un clone superficiel (shallow)
  Cause : la session de travail est clonee en --depth 1 et certaines branches
  distantes n'existaient pas localement.
  Solution : "git fetch origin 'refs/heads/*:refs/remotes/origin/*'" avant
  toute comparaison de branches. Ne pas supposer que l'historique est complet.

INCIDENT 13 - rmdir /s /q sur le mauvais dossier (piege du renommage)
  Contexte : en remplacant le dossier de sortie release\ par jeu\ dans
  build_launcher.bat, un remplacement global a transforme
  'if exist "release" rmdir /s /q "release"' en 'if exist "jeu" rmdir /s /q
  "jeu"' : le script aurait EFFACE jeu\ en entier (launcher.pyw,
  version_url.json, LIS-MOI.txt) a chaque build.
  Solution : la ligne supprime desormais uniquement %JEU%\game (l'ancien
  export), et un controle automatique verifie que toute cible de rmdir /s
  est bien un sous-dossier connu (game, game.install, game.ancien, Library,
  launcher, build).
  LECON : apres un remplacement de chemins dans un .bat, relire CHAQUE ligne
  de suppression. Un "rmdir /s /q" mal cible detruit le travail.

INCIDENT 14 - Pas d'acces reseau direct a GitHub dans le bac a sable
  Symptome : curl vers raw.githubusercontent.com / release-assets.githubusercontent.com
  echoue (SSL_ERROR_SYSCALL, EOF).
  Solution : passer par l'API (gh api) pour verifier qu'un fichier est bien
  publie sur une branche, et tester le launcher avec un serveur HTTP local
  (outils/test_launcher.py) au lieu de taper sur GitHub.

INCIDENT 15 - Le jeu compile affichait tout en magenta (rapporte par l'utilisateur)
  Symptome : capture d'ecran du joueur = collines, batiments et arbres en rose
  fluo ; le HUD, lui, s'affichait normalement.
  Cause    : le HUD est dessine par OnGUI (immediat, shader interne de
  l'interface, toujours present), alors que TOUS les objets 3D recoivent un
  materiau cree par code avec Shader.Find("Standard"). Unity retire de la
  build les shaders integres qu'aucun materiau du projet ne reference (aucun
  materiau ici : tout est cree a l'execution). Dans l'exe, Shader.Find
  renvoyait null -> materiau sans shader -> magenta. Un jeu entier en magenta
  = signe quasi certain de ce probleme, pas d'un probleme de couleur.
  Solution : shader du projet dans Assets/Resources/LVShaders/LVColor.shader
  (Resources = toujours embarque) + chaine de secours, et LOG du shader
  retenu. Pour tout nouveau materiau cree par code : passer par
  ResoudreShader(), jamais par Shader.Find seul.
  ATTENTION : ce bug n'apparait PAS dans l'editeur Unity, seulement dans
  l'exe compile. Toujours tester l'exe, pas seulement Play.

INCIDENT 16 - La camera demarrait sous le terrain (rapporte par l'utilisateur)
  Symptome : "la camera demarre sous le sol" puis remonte, et la souris met un
  temps fou a repondre (meme plainte, meme correctif).
  Cause    : deux bugs independants dans UpdateCamera() et Update() :
             - Quaternion.Euler(cameraPitch = +18) * Vector3.forward place la
               camera SOUS le heros (y negatif) : pour mettre une camera en
               orbite au-dessus, il faut Vector3.back (Unity regarde vers +Z).
             - Input.GetAxis("Mouse X") est lisse, et la sensibilite 0,3
               correspondait a 0,03 degre par pixel au lieu de 0,3.
  Solution : Vector3.back + plafond de securite (0,6 au-dessus du terrain) ;
  GetAxisRaw + sensibilite 3. Voir MAJ 7.

INCIDENT 17 - Les corrections ne partaient pas chez l'utilisateur (le plus sournois)
  Symptome : aucune erreur nulle part, mais le jeu recompile chez l'utilisateur
  restait exactement l'ancien (monde magenta). C'est le genre de piege qu'aucun
  message de log ne signale.
  Cause    : build_launcher.bat commencait par "si le projet existe deja, on ne
  telecharge rien" (pour ne pas ecraser le travail local). Les sources sur ce PC
  n'etaient donc jamais rafraichies, alors que c'est le depot GitHub qui fait
  foi.
  Solution : mise a jour a chaque lancement, avec deux garde-fous : sauvegarde
  de l'ancienne version dans build\sauvegarde_locale\ AVANT de remplacer, et
  le script de fabrication lui-meme n'est jamais ecrase pendant son execution
  (il est pose a cote en .maj). Voir MAJ 9.
  A retenir : apres avoir pousse une correction du jeu, TOUJOURS verifier
  qu'elle arrive jusqu'a l'exe du joueur (et pas seulement dans le depot).



INCIDENT 18 - Le jeu plante au demarrage chez l'utilisateur, sans aucune trace
  Symptome (18/09/2026) : "mon jeu crash au demarrage", sans autre detail : ni
  message, ni fichier. Impossible de diagnostiquer a distance.
  Cause du silence : rien ne garantissait qu'un journal soit ecrit, et l'endroit
  ou Unity l'ecrit d'habitude (AppData\LocalLow\LibreVies\LibreVies) n'est
  pas un endroit qu'un joueur connait.
  Solution (MAJ 12) : le launcher lance le jeu avec -logFile
  jeu\game\logs\LibreVies.log, donc le journal est TOUJOURS a cote du jeu, et
  le bouton RAPPORT ouvre directement les dossiers utiles.
  Fichiers a demander (ou ouverts par RAPPORT) :
    - jeu\game\logs\LibreVies.log : notre journal, le plus direct ;
    - %USERPROFILE%\AppData\LocalLow\LibreVies\LibreVies\Player.log et
      Player-prev.log : journal standard Unity (Player-prev = lancement d'avant) ;
    - %USERPROFILE%\AppData\Local\Temp\LibreVies\LibreVies\Crashes\
      <horodatage>\error.log (+ crash.dmp) : ecrit par le gestionnaire de
      plantage d'Unity, c'est LUI qui donne la pile d'appels ;
    - jeu\journal_launcher.txt : si c'est le LAUNCHER qui plante (l'amorce).
  Ordre de lecture : error.log d'abord (pile d'appels), sinon la fin de
  LibreVies.log. A savoir : une exception C# n'arrete PAS un jeu Unity, elle
  s'ecrit dans le journal ; un vrai plantage vient plutot d'un module natif, du
  Graphics API, ou d'un plantage du gestionnaire de plantage. Verifier aussi
  qu'il a bien compile les bonnes sources (MAJ 7 a 11) et demander QUOI il a
  lance : jeu\LibreVies.exe (le launcher) ou jeu\game\LibreViesGame.exe (le jeu).

INCIDENT 19 - Le jeu se fige au demarrage : une boucle qui ajoute dans la liste
  qu'elle parcourt (le plus grave de tous : il bloquait le jeu entier)
  Symptome (18/09/2026) : "mon jeu crash au demarrage" ; la fenetre affichait
  "Chargement du monde..." puis plus rien, barre figee, aucun message, aucun
  fichier de plantage. Deux journaux strictement identiques, sans aucune
  exception : ce n'etait donc ni un plantage C# ni un plantage natif.
  Comment on l'a trouve : le journal [LV] de la MAJ 13 entoure chaque etape de
  construction d'un "debut :" et d'un "fin :". Le dernier "debut : cloture et
  portails" sans "fin" -> le gel etait dans CreateFence(). Sans ce journal, on
  cherchait a l'aveugle dans 2000 lignes de code (et on ne pouvait pas
  reproduire : pas d'Unity ni de Windows dans le bac a sable).
  Cause : une variable locale nommee 'portails' masquait le champ 'portails', et
  la boucle qui construisait les portails parcourait 'portails.Count' tout en
  ajoutant dans 'portails' -> boucle infinie (la liste grandit d'un element par
  tour, la condition reste toujours vraie) et, accessoirement, plus aucun
  portail transmis aux gardes.
  Quand a-t-elle ete introduite : dans le lot de la cloture (MAJ 8, commit
  8e75875). Toutes les compilations depuis ce lot etaient donc injouables : le
  jeu se figeait ~0,4 s apres le lancement, en plein chargement.
  Correction : MAJ 15 (deux listes distinctes).
  Regle a retenir : un compilateur NE SIGNALE PAS cette faute, et Unity ne dit
  rien a l'execution. C'est pour cela que verifier_cs_syntaxe.py controle
  maintenant les boucles qui gonflent la liste qu'elles parcourent, ainsi que
  les variables locales qui masquent un champ.
  A retenir aussi : un journal d'etapes coute 20 lignes de code et fait gagner
  des heures. Toute etape construite par code doit avoir son "debut"/"fin".

7. REGLES TECHNIQUES A RESPECTER (pour ne pas reproduire les incidents)
================================================================================

  R1. Ne jamais modifier launcher.pyw par regex multi-lignes. Remplacement
      ligne par ligne + compile() de controle (voir incident 7).
  R2. Apres TOUTE modification du launcher, lancer :
        python compilation/outils/test_launcher.py     (40 controles, local)
        python compilation/outils/test_amorce.py      (13 controles, local)
      (ou compilation\outils\tester_launcher.bat qui lance les deux)
      et verifier python -m py_compile jeu/launcher.pyw.
  R3. Les .bat sont ecrits en ASCII, sans accents, et doivent passer le
      controleur de blocs/parentheses/labels (incident 8). On ne peut pas les
      executer sous Linux : la relecture automatique est obligatoire.
  R4. Le dossier jeu/ ne contient que launcher.pyw, version_url.json,
      LIS-MOI.txt (plus les fichiers telecharges, ignores par git).
  R5. Le launcher ne telecharge jamais rien venant de compilation/.
  R6. Toute entree du manifeste passe par _safe_local_path : pas de "..",
      pas de chemin absolu, pas de "C:".
  R7. Une archive de jeu publiee ne doit jamais etre ecrasee : son nom
      contient son md5 (LibreVies_jeu_<md5 8 car.>.zip).
  R8. Le jeu ne se met a jour que par une archive complete (game_build) ;
      le contenu de l'archive est place A LA RACINE du zip (pas de dossier
      enveloppe : le launcher remonte quand meme un dossier unique).
  R9. Une panne reseau ne doit jamais bloquer un jeu deja installe : hors
      ligne, le launcher affiche "Hors ligne" mais JOUER marche encore.
  R10. Ne jamais demander de mot de passe, token ou identifiant GitHub : la
      connexion git/gh est deja configuree dans l'environnement.
  R11. Ne pas changer de branche : le travail est publie sur
      arena/01a0b32c-librevies (branche de la session). Pour publier depuis
      une autre branche (main par exemple), utiliser
      outils/definir_url_publication.py --branche main.
  R12. AUCUN materiau 3D ne se cree avec Shader.Find seul : passer par
      ResoudreShader() (incident 15). Tout shader utilise par un materiau cree
      par code doit vivre dans Assets/Resources/ pour survivre a la compilation.
  R13. Une correction de rendu ne se valide QUE dans l'exe compile, jamais dans
      l'editeur Unity (le magenta n'apparaissait pas dans Play, incident 15).
  R14. Le launcher vit dans jeu/launcher.pyw et NULLE PART ailleurs. L'amorce
      (compilation/amorce/amorce_launcher.py) ne doit contenir que le lancement
      du .pyw, le journal et les messages d'erreur. Tout import ajoute a
      launcher.pyw doit etre ajoute aussi dans l'amorce, sinon l'exe compile ne
      le contiendra pas (le .pyw est charge dynamiquement : PyInstaller ne peut
      pas deviner ses imports).
  R15 bis. Un compilateur ne voit PAS une boucle qui ajoute dans la liste
      qu'elle parcourt (incident 19 : gel total du jeu). Avant TOUT commit qui
      touche du C# : python compilation/outils/verifier_cs_syntaxe.py, qui
      signale maintenant aussi les boucles infinies et les variables locales
      masquant un champ. Corollaire de style : ne JAMAIS nommer une variable
      locale comme un champ de la classe (ex. 'portails', 'gardes', 'enemies').
  R15 ter. Toute etape de construction d'un monde doit etre entouree d'un
      "debut"/"fin" dans le journal [LV] : c'est ce qui permet de trouver un
      gel a distance, sans pouvoir reproduire (voir MAJ 13 et incident 19).
  R15. Ne jamais demander a l'utilisateur de remplacer un fichier a la main.
      Tout ce qui peut se mettre a jour par hash doit le faire : launcher.pyw
      (cle "files"), le jeu (cle "game_build") et build_launcher.bat (SHA de la
      branche, qu'il applique desormais tout seul). Exception historique :
      la toute premiere mise a jour de build_launcher.bat sur sa machine, dont
      l'ancienne version ne savait que poser un .maj.

    publication du launcher compile, notation de l'installation locale
    (jeu\etat_jeu.json), option --pousser pour git.
    Chemins par defaut : --jeu jeu\game et --exe jeu\LibreVies.exe.
    Depuis la MAJ 12, il publie aussi launcher.pyw avec son hash : c'est ce qui
    fait arriver les nouveautes du launcher chez les joueurs SANS recompiler.

  compilation/outils/definir_url_publication.py / .bat
    Change la branche publiee dans les 3 endroits, avec garde-fous.

  compilation/amorce/amorce_launcher.py
    L'AMORCE : c'est ce fichier qui est compile en jeu\LibreVies.exe (voir
    section 3.0). Elle execute jeu\launcher.pyw, recopie la copie embarquee
    (--add-data) au premier lancement, et ecrit journal_launcher.txt + une
    boite d'alerte si le launcher plante. Ne JAMAIS y remettre de logique du
    launcher. Les imports du haut (tkinter, urllib, zipfile, subprocess...)
    servent a les faire EMBARQUER par PyInstaller : tout nouvel import de
    launcher.pyw doit etre ajoute ici, sinon l'exe compile ne le contiendra pas.

  compilation/outils/test_amorce.py
    Recette de l'amorce (13 controles) : le code du launcher est bien execute
    comme un programme, la copie embarquee est recopiee au premier lancement,
    un message clair s'affiche si le code manque, un plantage du launcher
    laisse un journal exploitable, et SystemExit traverse l'amorce.
        python compilation/outils/test_amorce.py

  compilation/outils/test_launcher.py / tester_launcher.bat
    Recette complete, hors ligne, sans tkinter. 40 controles :
    premiere installation, mise a jour, reprise apres coupure, archive
    corrompue (refusee sans casser l'installation), archive piegee (../),
    chemins interdits du manifeste, lancement du jeu (avec -logFile), mise a
    jour du code du launcher par hash, cas "rien de publie".
    tester_launcher.bat lance test_launcher.py PUIS test_amorce.py.

  compilation/outils/creer_icone.py / creer_icone.bat
    Reextrait icon.ico depuis les octets integres au launcher.

  compilation/outils/verifier_cs_syntaxe.py
    Controleur de SYNTAXE des fichiers C# (grammaire tree-sitter) : attrape les
    accolades/points-virgules manquants AVANT de lancer Unity, alors qu'il n'y
    a aucun compilateur C# dans le bac a sable. Il signale aussi les APPELS a
    des methodes qui n'existent nulle part (methode renommee ou supprimee) :
    c'est ce qui a permis de trouver CreateGuard() appele apres sa suppression.
    Il ne verifie PAS les types (a completer par une relecture).
        pip install --break-system-packages tree_sitter tree_sitter_c_sharp
        python compilation/outils/verifier_cs_syntaxe.py
    Teste sur une faute volontaire (point-virgule retire) : detectee.
    LIMITE : le paquet pip est perdu a chaque nouvelle session (bac a sable
    re-clone), il faut le reinstaller.

  compilation/outils/verifier_bat.py
    Controleur de scripts .bat : ASCII uniquement, parentheses non echappees
    dans un echo en bloc, labels appeles par call/goto mais inexistants,
    parentheses de bloc non equilibrees. A lancer apres chaque modification
    d'un .bat (incidents 8 et 9).

  compilation/unity/Assets/Scripts/LibreViesGame.cs
    Le jeu lui-meme (tout est construit par code C# : monde, heros, ennemis,
    combat, HUD OnGUI, sauvegarde).
    MISE EN GARDE (incident 15) : tous les materiaux 3D sont crees a
    l'execution. Ils DOIVENT passer par ResoudreShader() et jamais par un
    Shader.Find seul, sinon le jeu sort en magenta dans l'exe compile.
    Depuis la MAJ 24, CreateBuilding() ajoute aussi un MeshCollider aux toits
    pour que RendreObstaclesTranslucides() les detecte par raycast.

  compilation/unity/Assets/Resources/LVShaders/LVRealistic.shader
    Shader de materiau principal de la MAJ 31 : PBR Standard, mapping
    triplanaire monde pour les proceduraux sans UV, ombres avant et reglages
    metallic/smoothness/occlusion. Son .meta est versionne avec lui.

  compilation/unity/Assets/Resources/LVTextures/
    Cinq textures originales chargees par Resources.Load : platre des murs,
    tuiles terre cuite, beton des routes/pierres, bois et sol herbeux/terre.
    Les fichiers PNG et leurs .meta sont distribues avec le projet de
    compilation, pas avec un dossier joueur separe.

  compilation/unity/Assets/Resources/LVShaders/LVColor.shader
    Shader d'eclairage du projet (Lambert : _Color + _EmissionColor) utilise
    comme secours par ResoudreShader(). Dans Resources\ donc toujours embarque
    dans la build. Ses .meta ont des GUID ecrits a la main.

  compilation/unity/Assets/Resources/LVShaders/LVSky.shader
    Ciel degrade en 3 couleurs (haut, horizon, sol), secours de CreateSky()
    si Skybox/Procedural n'est pas disponible dans la build.

  - Verifier la syntaxe :    python -m py_compile jeu/launcher.pyw

    ne RIEN afficher. Oui, y compris dans ce fichier et dans les
    commentaires du code : ne jamais ecrire le nom du moteur abandonne.
  - Verifier que le launcher est bien en deux morceaux (MAJ 12) :
        jeu/launcher.pyw = tout le launcher ; compilation/amorce/
        amorce_launcher.py = l'exe qui l'execute. Un changement de launcher
        ne doit JAMAIS obliger a relancer PyInstaller.
  - Verifier les shaders du jeu :
        ls compilation/unity/Assets/Resources/LVShaders/   (4 fichiers : 2
        .shader + 2 .meta ; les .meta sont obligatoires, sinon Unity regenere
        des GUID et les references Resources.Load cassent)

        gh api "repos/killdrago/LibreVies/contents/jeu/version_url.json?ref=arena/01a0b32c-librevies"
  - Voir la release :        gh release view derniere
  - Tester le launcher sans toucher a GitHub : la recette utilise un serveur
    HTTP local (SimpleHTTPRequestHandler), aucun appel externe.

  reste (jeu, mises a jour) arrive par le manifeste et une archive verifiee
  par md5. Toute nouvelle fonctionnalite doit respecter ce principe simple.
