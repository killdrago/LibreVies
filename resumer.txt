1) C'EST QUOI
-------------
Jeu vidéo 3D "LibreVie" (MMO solo pour l'instant) fait avec GODOT 4, lancé par un
launcher Python/Tkinter (launcher.pyw) qui télécharge Godot si absent et qui
fait l'auto-update des fichiers du jeu depuis GitHub.
Dépôt GitHub : killdrago/LibreVies (branche de travail : main pour le public).

2) VERSIONS ACTUELLES
---------------------
- Moteur : GODOT 4.7.2-stable (migration faite le 13/09/2026).
  * project.godot : config/features=PackedStringArray("4.7")
  * launcher.pyw : GODOT_URL = .../4.7.2-stable/Godot_v4.7.2-stable_win64.exe.zip
  * Rendu : renderer/rendering_method="gl_compatibility" (volontaire : PC modestes)
- launcher.pyw : LAUNCHER_VERSION = "2.8.0", GAME_VERSION = "0.3.0"
- main.gd : const BUILD = "0.3.0-b18" (témoin de build, à incrémenter à chaque push)
- version_url.json : game_version "0.3.0" (hashs md5 + tailles de chaque fichier,
  calculés avec normalisation CRLF->LF pour les fichiers texte, comme le launcher).

3) FONCTIONNEMENT DE L'AUTO-UPDATE (IMPORTANT)
----------------------------------------------
- launcher.pyw lit son version_url.json LOCAL, puis télécharge le
  version_url.json DISTANT sur raw_url (branche de travail ou main).
- SYSTÈME = HASH MD5 par fichier (launcher 2.8.0). Une parenthèse "numéros de
  version" (2.7.0) a été essayée puis ABANDONNÉE le 14/09/2026 à la demande du
  dev : avec les numéros, un fichier corrompu n'était pas réparé. Le hash, si.
  NE PAS revenir aux numéros.
- Comparaison : hash md5 LOCAL du fichier sur disque (texte .gd,.tscn,.godot,
  .pyw,.py,.bat,.json,... : md5 après normalisation CRLF->LF ; binaires png/glb/
  ico : md5 brut) vs hash du manifeste distant. Différent ou fichier absent =>
  téléchargement depuis raw_url/<fichier>, puis VÉRIFICATION du hash après
  téléchargement (réparation des fichiers corrompus incluse).
- Après update, le version_url.json local est remplacé par le distant.

- !!! REGLE IMPERATIVE (décision du dev, À RESPECTER ABSOLUMENT) !!!
  * TOUT changement dans un fichier listé (même une seule ligne) = NOUVEAU HASH
    dans version_url.json (pour que la MAJ soit téléchargée).
  * TOUT nouveau fichier utile au jeu = AJOUTER SA LIGNE dans version_url.json
    ainsi que SON HASH.
  * TOUT fichier supprimé = RETIRER SA LIGNE de version_url.json.
  * Sans ça, la modification n'est PAS distribuée aux joueurs.

- launcher.pyw est volontairement ignoré par l'update (évite la boucle) :
  on le remplace à la main, ou via le .exe recompilé par build_launcher.bat.
  (Il est quand même listé avec son hash, pour info/vérification manuelle.)
- FORMAT raw_url (piège déjà rencontré, 404) : une URL raw NE CONTIENT PAS
  "/tree/". Bon format : https://raw.githubusercontent.com/killdrago/LibreVies/<BRANCHE>
  (ex. branche de test : .../LibreVies/arena/01a09a4d-librevies ; prod : .../LibreVies/main).
  Le launcher 2.5.1+ a une fonction normalize_raw_url() qui répare tout seul
  les URLs copiées depuis le site (github.com/.../tree/BRANCHE ou
  raw.githubusercontent.com/.../tree/BRANCHE).
- DEPUIS LA 2.5.1 : le manifeste distant (version_url.json sur GitHub) donne le
  raw_url de téléchargement ; le manifeste de la branche de travail pointe vers
  CETTE branche (auto-référent) pour que les testeurs reçoivent la MAJ de la
  branche. APRÈS MERGE SUR main : vérifier que le raw_url du manifeste main est
  bien ".../LibreVies/main" (sinon les joueurs resteraient branchés sur la branche).
- Script de regénération utilisé (à refaire à chaque MAJ) : parcourir la liste
  "files" de version_url.json, recalculer md5/taille de chaque fichier présent
  dans le repo (texte = md5 après CRLF->LF), réécrire le json (indent=2, clés :
  launcher_version, game_version, notes, game_url, raw_url, files{nom:{hash,size}}).
- Migration 2.7.0->2.8.0 : un manifeste local au format "numéros" n'a pas de
  clé "hash" => tous les fichiers sont retéléchargés UNE seule fois au premier
  lancement en 2.8.0, puis le système à hashs reprend la main.

6) REGLES / PIEGES A RETENIR
----------------------------
- Le launcher compare les hashs : tout fichier modifié doit être dans
  version_url.json avec son nouveau hash, sinon les joueurs ne le recevront pas.
- Tout nouveau fichier .gd ajouté au jeu devrait être ajouté à la liste "files".
  (Actuellement tout le jeu tient dans main.gd exprès pour simplifier l'update.)
- Ne pas remettre de nœuds CSG : perf et style low-poly obligent (PrimitiveMesh
  partagés via _mesh_cache / _mat_cache).
- Le joueur et les objets sont posés via hauteur_terrain(x,z) : toute nouvelle
  construction au sol doit utiliser cette fonction (zone plate sous TOWN_R).
- Collisions bâtiments = liste "batiments" (AABB 2D manuelles), pas de physique.
- gl_compatibility : pas de SDFGI/voxel ; ciel = ProceduralSkyMaterial OK.
- Godot 4.7 : API GDScript 2.0 (typed, Signal.connect, queue_redraw,
  ThemeDB.fallback_font, draw_style_box, MiniMesh non : MultiMesh).
- PIEGE GDScript TYPAGE (rencontré 13/09/2026) : "var x := <expr>" échoue en
  compile ("Cannot infer the type") dès que l'expr contient un Variant
  (valeur lue dans un Dictionary/Array non typé, ex. e.pv, f.t). Solutions
  appliquées : annoter explicitement ("var x: float = ..."), typer les
  tableaux ("var CHEMIN: Array[Vector2] = [...]"), ou typer les params
  ("func _process(delta: float)"). Ne JAMAIS faire "var x := dict.champ".
  Idem : "$Nom" renvoie un Node statiquement => typer ("var sun:
  DirectionalLight3D = $DirectionalLight3D").
- AUTRE PIEGE Godot 4.7 : BaseMaterial3D.ShadingMode ne contient QUE
  SHADING_MODE_PIXEL et SHADING_MODE_VERTEX. Il n'y a PAS de
  SHADING_MODE_UNLIT (ni sur StandardMaterial3D). Pour un rendu "unlit"
  (nuages blancs plats) : emission_enabled + emission = couleur +
  emission_energy_multiplier = 1.0, ou un vrai ShaderMaterial render_mode
  unlit. Ne jamais écrire StandardMaterial3D.SHADING_MODE_UNLIT /
  BaseMaterial3D.SHADING_MODE_UNLIT : erreur de parse garantie.
